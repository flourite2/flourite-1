## 직접 수행한 작업



### StringUtils::Split 구현

- 총 6~7차례 반복 수정을 거쳐 최종 형태에 도달

- 초기 시도의 문제들을 스스로 걷어냄: 다이얼로그 로직 혼입, 루프 안 조기 `return`, 타입 불일치(`stringstream`을 결과 벡터에 삽입 시도), 불필요한 사전 검사(`find(delim)` 체크)

- 최종: 빈 벡터에 `getline` 결과를 누적 후 리턴하는 단순 구조

- 리턴 방식 결정 근거: NRVO(2월 학습 내용 활용) — out-파라미터 방식 대비 비용 차이 없음, 가독성 우위

- `char delim`은 값 전달로 수정 (습관적 `const char&` 제거)



### DialogParser 선택지 파싱 리팩토링

- 기존 `find(':')` + `substr` 방식 → `Split` 두 번 호출(`|` → `:`) 방식으로 재작성

- `choiceTokens.size() == 2` 방어 로직 추가



### 크래시 자체 추적 및 수정

- `Debug Assertion Failed (vector subscript out of range)` 발생

- 콜스택 없이 에러 로그(`choiceTokens.size()가 2가 아님: -`)만으로 원인 추적

- 원인: 조건문 `!=`/`==` 반전 실수 → `-`(선택지 없음)일 때만 파싱하는 역논리가 되어, 크기 1 벡터의 `[1]` 접근으로 크래시

- 논리 수정 후 정상 동작 확인



### 테이블 설계 (전체 설계 결정 직접 수행)

- **아이템 정의** (wide): `ItemID | ItemName | Description`

- **아이템 스탯 효과** (long): `ItemID | ModifyStat | ModifyCategory | Value`

&#x20; - `ModifyStat`은 실제 컴포넌트 필드명과 1:1 대응 (`baseAtk`, `baseElementAtkRatio.NORMAL` 등 — 배열 인덱스는 `.` 구분자)

&#x20; - `ModifyCategory`: `ADD` / `MUL` / `ADD_FINAL` enum (ADD는 음수 허용, SUB 별도 카테고리 없음)

- **장비 슬롯**: `BeingID | Slot | ItemID` — weapon/armor/accessory 각 1개 고정, `EquipSlot` enum

- **공격 스킬**: `SkillID | SkillName | ElementalType | AtkMultiplier | AdditionalEffect | AdditionalEffectRate`

&#x20; - 부가효과는 스킬당 최대 1개로 제한 (다중 지원 시 컬럼 간 암묵적 순서 약속이 깨지기 쉬움)

- **방어 스킬**: 공격 스킬과 동일 패턴, `DefMultiplier`

- **버프/디버프 스킬** (통합): `SkillID | SkillName | ModifyStat | Target | ModifyCategory | Value | Duration`

&#x20; - `Target`(self/enemy)으로 버프/디버프 구분

- 설계 원칙 확인: 이름 중복 저장 회피(정규화), 파서가 읽기 편한 형태 우선, config 컬럼명 = 코드 변수명

## 미해결 / 다음 세션 의제 (중요도 순)



1. **`ParseDefenseConfig` 버그 수정** — `defTable[data.id] = data;` 누락으로 파싱 결과가 테이블에 저장되지 않음. 현재 크래시가 없는 이유는 `defTable`을 실제로 읽는 코드가 아직 없기 때문일 뿐. **다음 세션 시작 시 최우선 수정**

2. **전투용 임시 스탯 처리 방식** — `modified` 계열이 "전투 중에만 의미 있는 값"이라는 설계 의도 확인됨. 새 컴포넌트 신설 여부, 생명주기(전투 시작/종료 리셋), 계산 수식 위치(컴포넌트 vs 시스템/유틸) — 전투 코어 루프 설계의 시작점이므로 테이블 단계에서 무리하게 확정하지 않고 이월

3. **상태이상 테이블 재검토** — 상태이상 요구 대부분이 버프/디버프 스킬 테이블로 흡수됨. 별도 테이블이 여전히 필요한지 재판단 (공격 스킬의 `AdditionalEffect`가 참조할 대상 정의는 필요)

4. **`ModifyCategory` 공유 vs 분리** — `ADD_FINAL`이 스킬 쪽에는 불필요해 보임. 아이템용/스킬용 enum 분리 여부

5. **여러 장비 효과 합산 방식** — 아이템별 개별 계산 후 합산 vs 카테고리별 일괄 계산 (전투 데미지 계산식 설계 시 함께 결정)

6. **문자열 → enum 변환 함수들 구현** — `EquipSlot`, `ModifyCategory`, `ElementType`(스킬용), `SkillTarget` 등. if/else vs map 방식, 매칭 실패 시 처리 방침 미정

7. Application 리팩토링 → Combat/Elemental 컴포넌트 EntityManager 편입 (조립 단계 직전 수행 — 순서 확정됨)
