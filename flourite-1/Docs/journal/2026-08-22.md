## 오늘 한 일

### 1. `ElementType` 원소 개수(5)의 분산 정리

원소가 다섯 종류라는 하나의 사실이 컴포넌트, 파서 헤더, 파서 구현에 흩어져 있던 문제다. 원소를 추가할 때 한 곳만 빠뜨려도 컴파일은 통과하고 런타임에 배열 범위를 넘는다.

**세 개의 사실로 갈렸다.** 처음에는 흩어진 `5`를 상수 하나로 치환하는 작업이라고 생각했다. 그런데 숫자마다 "무엇을 바꾸면 이게 함께 움직이는가"를 따져 보니 서로 다른 사실이 섞여 있었다.

원소를 하나 추가하면 `array<float, 5>`, 루프 조건, `cols[6 + i]`의 `6`, `COLSIZE`가 전부 움직이는데 `cols[1 + i]`의 `1`만 가만히 있다. 반대로 테이블 앞에 컬럼을 하나 붙이면 `1 + i`와 `6 + i`가 함께 움직인다. 이렇게 갈라 보니 셋이었다.

- 원소가 몇 종류인가 (5)
- 원소 컬럼들 앞에 놓인 컬럼이 몇 개인가 (1)
- 원소 블록이 몇 개인가 (2 — 공격배율, 방어배율)

그리고 `6`과 `COLSIZE`의 `11`은 독립된 사실이 아니라 위 셋에서 계산되는 값이었다. 상수로 선언할 게 아니라 계산식으로 써야 했다.

```
COLSIZE = KEYCOLS + (ELEMENTCOUNT * BLOCKCOUNT)
```

**`6`은 계산이 아니라 눈으로 센 값이었다.** 작업 중에 확인한 건데, 내가 원래 `cols[6 + i]`를 쓸 때 머릿속에 있던 건 "방어배율은 6번 칸부터 시작한다"였다. 파일을 보고 세어서 넣은 위치값이지 `1 + 5`를 계산한 결과가 아니었다.

눈으로 센 값은 파일이 바뀌면 조용히 틀려진다. 컴파일러가 확인해 줄 방법이 없다. 그래서 오늘 한 작업의 실질은 매직 넘버 제거라기보다 관찰한 값을 유도된 값으로 바꾸는 것이었다. 이 구분은 오늘 처음 명확해졌다.

**상수 배치.** 세 사실이 각각 어디에 속하는지도 따로 판단했다.

- 원소 개수 — 게임 규칙 자체다. TSV 파일을 지워도 "이 게임에는 원소가 다섯 종류다"는 남는다. `ElementType` enum 옆(`CombatComponents.h`)에 뒀다
- 앞 컬럼 수, 블록 개수 — `base_elemental_table.tsv`의 생김새에 대한 지식이다. 파서 안에만 뒀다. 컴포넌트 헤더가 이걸 알면 TSV 형식이 바뀔 때 컴포넌트가 딸려 움직인다

배치 근거를 세우는 과정에서 내가 착각하고 있던 것도 하나 나왔다. 컬럼 오프셋이 `std::array`에 맞춰진 값이라고 생각했는데 아니었다. `cols`는 TSV 한 줄을 `\t`로 자른 결과라 파일 형식만 알고 메모리 표현은 모른다. 컴포넌트 쪽 컨테이너를 뭘로 바꾸든 오프셋은 변하지 않는다.

**`enum class`와 `constexpr`.** `ElementType`에 `COUNT`를 추가하고, 값을 적지 않아 컴파일러가 자동으로 매기게 했다.

`std::array<float, ElementType::COUNT>`가 컴파일되지 않는 이유는 오늘 확인했다. `enum class`는 암묵적 정수 변환을 하지 않는데 `std::array`의 두 번째 인자는 `std::size_t`를 요구한다. 그 변환 차단이 `enum class`의 존재 이유이기도 하다. `static_cast`로 한 번만 변환해 이름을 붙이고, 네 배열이 그 이름을 공유하게 했다.

`constexpr`이 필요한 이유도 두 가지로 정리됐다. 템플릿 인자는 컴파일 타임에 확정된 값이어야 하고, 람다가 캡처 없이 참조하려면 `constexpr`이어야 한다. 후자는 `const`로만 선언한 상수를 캡처 없이 쓰려다 실제로 컴파일 에러를 봤다. `const`는 "안 바뀐다"는 약속일 뿐 컴파일 타임 확정을 보장하지 않는다.

**`COUNT`가 왜 개수와 같은가.** Claude에게 `COUNT` 항목을 추가해 매직 넘버를 없애 보라는 제안을 받아 그대로 넣고 for문 조건에 써 봤다. 어디에도 매핑을 하지 않았는데 이게 어떻게 배열 크기와 맞아떨어지는지 처음에는 의문이었다.

결국 `enum class`도 정수들의 집합이라는 게 답이었다. 컴파일러가 나열 순서대로 0부터 값을 매기니 마지막 실제 원소가 (원소 개수 - 1)이 되고, 그 다음 자리인 `COUNT`가 원소 개수와 같은 값을 받는다. 내가 5를 적어 넣은 게 아니라 항목을 나열한 것에서 따라 나온 값이다. 그래서 원소를 추가하면 `COUNT`도, 그걸 쓰는 배열 크기와 루프 조건과 `COLSIZE`도 전부 함께 움직인다.

대신 지켜야 할 게 생긴다. `COUNT`는 원소가 아니라 개수를 담는 자리 표시용 항목이므로 반드시 마지막에 있어야 하고, 새 원소는 그 앞에 넣어야 한다. 순회 루프도 `COUNT`를 돌면 안 된다. 나중에 문자열→enum 변환 함수를 만들 때 `"COUNT"`가 매칭되지 않게 하는 것도 같은 이유다.

`MotionTypes.h`가 `Count = 4`로 값을 적어 둔 게 왜 문제인지도 여기서 분명해졌다. 항목을 하나 추가하면 실제 개수는 5가 되는데 `Count`는 4로 남고, 컴파일은 통과한 채로 배열이 하나 모자라게 된다. 자동 계산의 이점이 통째로 사라진다.

**파서 정리.** `ElementalMapData`의 배열 크기를 상수로 바꾸고, 같은 범위를 도는 for문 두 개를 하나로 합쳤다. `i`가 같은데 나눠 돌 이유가 없었다. 인덱스는 `cols[KEYCOLS + i]`, `cols[KEYCOLS + ELEMENTCOUNT + i]` 형태가 됐다.

블록 인덱싱을 "n번째 블록의 i번째 컬럼"이라는 하나의 식으로 일반화하는 방향도 검토했다. 블록이 두 개뿐이라 이득이 크지 않다고 보고 보류했다. 셋 이상 되면 다시 볼 항목이다.

**검증 데이터.** 처음 파싱 결과를 봤을 때 값이 전부 1.0이라 출력도 전부 1이었고, 그걸 보고 "잘 읽힌다"고 판단할 뻔했다. 지적을 받고 보니 전부 같은 값이면 블록이 뒤바뀌어도, 오프셋이 밀려도 출력이 똑같아서 아무것도 증명되지 않는 상태였다.

테스트 데이터를 공격배율 1.0~5.0, 방어배율 6.0~10.0으로 전부 다르게 바꾸고 다시 확인했다. 그러자 한 번의 출력으로 블록 분리, 블록 내 순서, 앞 컬럼 건너뛰기 세 가지가 동시에 확인됐다.

확인 과정에서 내가 만든 검증 로그 자체에 실수가 있는 것도 발견했다. `base` 값을 출력해야 할 자리에서 `modified`를 읽고 있었다. 진단 코드도 코드라서 틀린다.

파싱 체크 `cout`은 지우지 않고 주석 처리해 뒀다. 테이블 구조를 다시 손볼 때 쓸 수 있다고 봤다.

**`ElementalComponent` / `ElementalMapData` 중복.** 딕셔너리에 "분리가 의도인지 확인 필요"로 남겨 뒀던 항목이다. 유지하기로 했다.

`ElementalMapData`는 TSV 형식을 따라가고 `ElementalComponent`는 게임 로직을 따라간다. 다만 현재 코드는 필드를 그대로 복사하고 있어서 둘이 갈라지는 변경이 아직 실제로 없다. 장비로 인한 영구 변동과 버프로 인한 일시 변동 계산을 넣을 계획이 있어 그때 갈라진다고 보고 유지했다. 지금 시점에서는 검증된 근거가 아니라 계획에 기반한 판단이라는 점은 적어 둔다.

### 2. 필수 에셋 검증 — 설계까지

8/9에 `at()` 전환을 하면서 삽입 의존이라 `[]`를 유지한 네 곳이 있었다. 로딩이 실패하면 빈 리소스가 맵에 남고, 그러면 나중에 조회하는 쪽의 `at()`이 예외를 던지지 않는다. 키는 존재하니까. 증상은 화면에 아무것도 안 나오는 형태로, 원인에서 멀리 떨어진 곳에서 나타난다.

오늘은 설계까지만 하고 구현은 다음으로 넘겼다.

**현재 `InitAssets()` 상태.** 로딩 루프를 다시 보니 문제가 몇 가지 있었다.

- 로드 실패 시 `cerr`로 찍기만 하고 루프가 계속 진행된다. 중단이 없다
- 등급이 `[Warning]`인데, 필수 에셋이 없으면 정상 동작이 불가능하므로 사실과 맞지 않는다
- `type` 분기에 `else`가 없다. 매니페스트에 오타가 있으면 아무 일도 일어나지 않고 아무 말도 하지 않는다
- CSV, TSV, JSON 로딩 넷은 성공 여부를 반환하지 않아 실패를 감지할 방법 자체가 없다

매니페스트 기반이라 에셋 목록은 이미 있었다. 처음에는 검증용 목록을 따로 만들 생각을 했는데, 그러면 목록이 두 곳으로 갈라져 한쪽만 고쳤을 때 검증이 조용히 거짓말을 하게 된다.

**정한 것.**

- 실패를 즉시 중단하지 않고 모아 뒀다가 끝에서 한 번에 출력한다. 실패가 셋이면 즉시 중단 방식은 세 번 실행해야 전부 알게 되지만, 모으면 한 번으로 끝난다
- 종료 결정은 `InitAssets()`가 하지 않는다. `bool`을 반환하고 `Application::Init()`을 거쳐 `main`이 판단한다. 이미 그 구조가 있어서 새로 만들 게 없었다
- 실패 정보는 `vector<구조체>`로 모은다. 키로 조회할 일이 없고 매니페스트 순서를 유지해야 하므로 map은 맞지 않는다
- 실패 종류는 `enum class`로 둔다. 자유 문자열이면 부르는 곳마다 문구가 달라지고 오타가 안 걸린다
- enum에는 "무슨 일이 일어났나"만 담는다. "무엇에게"는 구조체의 `type` 필드가 이미 말한다
- enum을 사람이 읽을 문구로 바꾸는 건 출력 시점에 `switch`로 한다. C++에는 리플렉션이 없어 enum 이름을 런타임에 문자열로 꺼낼 수 없다. 직접 써야 한다
- 구조체와 enum은 `Application.cpp` 안에 둔다. 현재 이걸 만드는 것도 쓰는 것도 그 파일 하나다

**이름 짓기에서 걸린 것.** 실패 종류를 `TEXTURE_MISSING`, `PATH_MISSING` 식으로 나누려 했는데 두 가지가 걸렸다.

`TEXTURE`는 `type` 필드와 중복이고, 텍스처만 특별할 이유도 없다. 더 중요한 건 `PATH_MISSING` 쪽이었다. `loadFromFile`이 돌려주는 `false`는 "못 읽었다"까지만 말한다. 파일이 없어서인지 손상돼서인지는 알려주지 않는다. 그런데 "경로 없음"이라고 출력하면, 실제로는 파일이 깨진 경우에 경로를 뒤지느라 시간을 쓰게 된다. 이름이 실제로 아는 것보다 많이 주장하면 안 된다.

## 오늘 겪은 것

**람다 캡처를 지우려다 대괄호까지 지웠다.** `constexpr`로 바꿔서 캡처가 필요 없어졌길래 `[COLSIZE]`를 지웠는데, 대괄호까지 통째로 날렸다. 에러가 여덟 개 났다.

```
identifier "mapping" is undefined
identifier "filepath" is undefined
explicit type is missing ('int' assumed)
expected an expression
...
```

대괄호가 없으면 컴파일러가 람다로 인식하지 못하고 `= (...)`를 괄호식으로 읽으려다 실패한다. 그 뒤가 전부 무너진 것이었다. 한 곳을 고치니 전부 사라졌다.

8/9에 정리해 둔 "에러 개수에 압도되지 말고 위쪽부터" 항목이 그대로 적용됐다. 추가로 알게 된 것은, `expected an expression`이나 `explicit type is missing` 같은 게 섞여 나오면 타입 문제가 아니라 문법이 깨졌다는 신호라는 점이다.

**캡처를 지우는 것과 캡처 목록을 지우는 건 다른 작업이다.**

## Claude에게 받은 도움

- 반사실적 검사로 사실을 분해하는 방법. "무엇을 바꾸면 어떤 값이 함께 움직이는가"를 돌려 보라는 것. 내가 처음에 "서로 다른 사실 두 개"라고 답했고, 검사를 직접 돌려 세 개를 찾았다
- `6`과 `COLSIZE`가 파생값이라 선언이 아니라 계산이어야 한다는 지적. 8/9에도 받았던 것인데 오늘 실제로 적용했다
- 컬럼 오프셋이 컨테이너 종류와 무관하다는 교정. 나는 오프셋이 `array`에 맞춰진 값이라고 잘못 알고 있었다
- `enum class`가 암묵적 정수 변환을 하지 않는 이유. 결론만 적어 뒀고 근거는 잊고 있었다
- `constexpr`과 `const`의 차이, 그리고 람다 캡처와의 관계
- 검증 데이터가 서로 구별 가능해야 한다는 지적. 값이 전부 1인 출력을 보고 통과라고 판단할 뻔했다
- 상수 이름 검토 — `BEFOREVALUES`가 개수를 말하지 않는다는 점, `SETCOUNT`가 가리키는 대상이 내 설명과 어긋난다는 점
- `InitAssets()` 현재 코드의 문제점. 중단 없음, 등급 표기, `else` 누락, 감지 불가능한 넷
- 검증용 목록을 따로 만들면 목록이 두 곳으로 갈라진다는 지적
- 종료 결정을 누가 하는가에 대한 판단 기준
- `PATH_MISSING`이 코드가 모르는 것을 안다고 주장하는 이름이라는 지적

코드는 전부 직접 작성했다. 상수 이름 결정, 배치 판단, for문 병합 판단, 테스트 데이터 작성과 결과 해석, 검증 로그 실수 발견, 중복 구조체 유지 결정은 직접 했다. 다만 오늘도 판단 기준을 세우는 과정은 질문으로 유도받은 비중이 컸다.
