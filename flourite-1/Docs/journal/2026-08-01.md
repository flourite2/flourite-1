## 오늘 한 일

### clone 후 빌드 검증 도입

지금까지 "내 로컬에서 빌드되면 된 것"으로 여겼는데, 그게 아무것도 증명하지 않는다는 걸 확인했다.
`_OldFiles` 참조가 남아 있는지 문자열 검색으로 확인하려다가, 검색은 내가 이미 아는 실패 원인
하나만 볼 수 있다는 점을 깨달았다. 대신 저장소를 별도 경로에 clone해서 Rebuild를 돌렸다.
클론한 사람이 실제로 받는 것과 같은 상태이므로, 결과를 직접 볼 수 있다.

첫 시도는 실패했고 `Cannot open include file` 에러가 30개 넘게 나왔다.

### 발견한 문제 3건

**1. 저장소 루트가 솔루션 폴더보다 한 층 안쪽에 있었다**

`.sln`이 git 루트 바깥에 있어서 애초에 추적 대상이 아니었다. 클론한 사람은 열 파일이 없는 상태로
폴더를 받게 된다. `git status`가 "working tree clean"이라고 답한 것도, 그 파일이 이 저장소의
관심 범위 밖이었기 때문이다.

**2. 방치된 옛 저장소가 로컬에 남아 있었다**

솔루션 폴더에 `.git`이 하나 더 있었다. 폴더 구조가 정상이라 처음엔 살아있는 저장소로 봤는데,
내용을 확인해보니 7/18에 만들고 7/25 재구성 때 버려진 것이었다. 경로가 전부 옛 이름(`26_engine`),
브랜치는 `master`, 커밋 1개, 원격 없음, `_OldFiles` 47개가 전부 추적 중이었다.
`git init` 한 번이면 `.git` 폴더 구조는 다 생긴다는 걸 잊고 있었다.

**3. `.gitignore`가 두 벌 있었다**

바깥과 안쪽에 각각 하나씩. 지금까지 수정해온 건 안쪽이었고, 바깥 것은 오래된 상태로 남아 있었다.

### 조치

`.gitignore`를 하나로 합치면서 패턴 규칙을 확인했다. 슬래시가 중간에 있는 패턴은
`.gitignore` 위치 기준으로 경로가 고정되고, 끝에만 있거나 없는 패턴은 어느 깊이에서든 매칭된다.
루트를 한 층 올리면 앞쪽 세 줄만 깨진다는 뜻이었다.

- `Header Files/_OldFiles/`, `Source Files/_OldFiles/` → `_OldFiles/`
  (어느 위치에 있든 제외되는 게 안전하다고 판단)

이후 옛 `.git`을 제거하고, 안쪽 `.git`을 상위로 옮긴 뒤 `git add -A`로 삭제와 추가를 함께
스테이징했다. git이 전부 rename(100%)으로 인식해서 히스토리가 끊기지 않았다.
커밋 개수를 유지한 채 구조만 바뀌었다.

커밋 후 clone을 다시 받아 Rebuild 성공을 확인했다.

## 오늘 얻은 것

- **내 환경에서 되는 것은 아무것도 증명하지 않는다.** 문자열 검색은 내가 아는 실패 원인만
  확인하지만, clone 후 빌드는 결과를 본다.
- **구조의 존재는 내용에 대해 말해주지 않는다.** `.git`이 있다고 살아있는 저장소가 아니다.
  지난주에 "참조가 있다고 살아있는 코드가 아니다"를 확인했는데, 같은 형태의 착각이었다.
- **접혀 있는 출력은 확인이 아니다.** untracked 폴더는 `git status`에 폴더명만 나오고 내용은
  나열되지 않는다. 그 상태로 "깨끗하다"고 판단할 뻔했다.
