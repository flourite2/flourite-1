# 2026-08-30 — 스프라이트 CSV 로더의 실패 처리

## 오늘 한 일

에셋 로딩 중 실패가 조용히 넘어가던 경로를 하나 닫았다. 대상은 `RenderParser::LoadSpriteCSV`.

### 1. `MotionTypes.h` 정리

`Direction`과 `AnimFrame` 두 `enum class`를 손봤다.

- `Count`에 박혀 있던 값(`Count = 4`, `Count = 3`)을 제거했다. 값을 적어두면 항목이 늘어도 자동으로 따라오지 않는데, 컴파일은 통과하므로 배열만 모자란 채로 돌게 된다.
- `Direction`의 항목 값(`Down = 0` 등)도 제거했다. 이 값들은 CSV의 열 순서와 무관하다 — 열 매핑은 `AnimationUpdater`의 `switch`가 따로 하고 있다.
- 반대로 `AnimFrame`의 항목 값은 남겼다. 이쪽은 `static_cast<int>`로 값이 그대로 행 인덱스가 되므로 CSV의 행 순서에 종속돼 있다. 임의로 바꿀 수 있는 값이 아니다.
- 두 enum의 숫자가 같은 모양인데 성격이 정반대라, 각각 무엇에 묶여 있는지를 주석으로 남겼다. `Walk1`과 `Walk2`가 뒤바뀐 파일은 어떤 검증으로도 잡히지 않으므로 주석이 유일한 방어선이다.
- `DIRECTION_COUNT`, `ANIMATION_FRAME_COUNT`를 `constexpr`로 도입했다. `enum class`는 암묵적 정수 변환을 하지 않으므로 `static_cast`를 한 번만 하고 이름을 붙였다.

작업 전에 걱정한 것은 `enum` → `enum class` 전환 범위였는데, 파일을 열어보니 이미 `enum class`여서 해당 사항이 없었다. 착수 전에 확인해서 범위가 줄어든 경우다.

### 2. `LoadSpriteCSV`를 `std::optional` 반환으로 전환

기존 시그니처는 `std::vector<std::vector<int>>`였고, 실패해도 빈 벡터나 불완전한 테이블을 그대로 반환했다.

바꾼 내용:

- 반환 타입을 `std::optional<std::vector<std::vector<int>>>`로 변경.
- `std::stoi` 직접 호출을 `StringUtils::TryParseInt`로 교체. 기존에는 숫자가 아닌 셀이 들어오면 예외가 밖으로 나가 초기화 도중 프로그램이 종료됐다.
- 검사 세 가지를 새로 넣었다. 행마다 열 개수가 `DIRECTION_COUNT`와 일치하는지, 각 셀이 정수로 변환되는지, 파일 전체 행 개수가 `ANIMATION_FRAME_COUNT`와 일치하는지.
- 실패해도 즉시 중단하지 않고 끝까지 읽는다. 실패 여부는 `bool` 하나로 들고 가 마지막에 `nullopt`를 반환한다. 한 번 실행하면 파일의 문제가 전부 화면에 나온다.

**핵심 변경은 반환 타입이 아니었다.** 원래 코드에는 `if (!cell.empty())`와 `if (!row.empty())`가 있어서 빈 셀과 빈 행을 말없이 건너뛰고 있었다. 이 둘을 제거한 것이 실제 변경이다. `std::optional`은 실패를 전달하는 통로일 뿐이고, 실패로 판정되지 않던 것을 실패로 만들어주지는 않는다.

### 3. 빈 줄 처리

Tiled가 내보낸 CSV 파일 다섯 개를 열어보니 전부 마지막 줄이 빈 줄이었다. 이것을 실패로 치면 정상 파일이 실패한다.

그렇다고 "빈 줄은 건너뛴다"로 하면 파일 중간의 빈 줄도 함께 건너뛰어 행이 밀린다. 방금 막으려던 문제가 되살아난다.

그래서 빈 줄을 만나면 읽기를 종료하도록 했다. 파일 끝의 빈 줄이면 이미 다 읽은 뒤라 문제없고, 중간의 빈 줄이면 거기서 끊겨 행 개수가 모자라므로 행 개수 검사에 걸린다. 별도 검사를 추가하지 않고 기존 검사가 겸하는 형태다.

`std::getline`이 `\n`만 구분자로 보기 때문에 CRLF 파일에서는 `\r`이 줄 끝에 남는다. 이 경우 `line.empty()`가 거짓인데 내용은 없다. 파일이 어떤 개행을 쓰는지에 의존하지 않기 위해, 줄 단위로 공백 문자를 제거한 뒤 빈 줄을 판정하도록 했다. 정제 위치를 셀 단위에서 줄 단위로 올린 셈이고, 결과적으로 정제하는 곳이 한 군데로 모였다.

### 4. 호출부와 잔여 정리

- `Application::InitAssets()`의 `animTables[id] = LoadSpriteCSV(path)` 대입이 확인 없이는 불가능해졌다. 로딩에 실패한 에셋은 맵에 들어가지 않는다.
- `InitAssets()`에 실패 플래그를 도입했다. 다만 아래 적은 대로 아직 일부 분기에만 연결돼 있다.
- 사용처가 없는 `RenderParser::LoadMapCSV`를 삭제했다. 맵 로딩이 JSON으로 넘어가면서 죽은 함수가 되어 있었는데, 링커 에러를 고치느라 파일을 통째로 열었다가 발견했다.

### 5. 네임스페이스 표기 변경

`RenderParser.cpp`와 `AnimationHelper.cpp`에서 `namespace X { ... }` 블록으로 감싸던 것을 `X::함수명` 접두사 형태로 바꿨다.

`RenderParser.cpp` 쪽은 링커 에러를 고치는 과정에서 시작됐다. 블록을 걷어내면서 정적 변수 정의에 `RenderParser::` 접두사를 붙이는 것을 빠뜨려 `unresolved external symbol`이 넷 나왔다. 에러 줄은 여덟 개였지만 마지막 줄의 `4 unresolved externals`가 실제 개수를 알려줬다. 참조하는 `.cpp`가 둘이라 같은 심볼이 두 번씩 출력된 것이었다.

`AnimationHelper.cpp`는 그 김에 같은 형태로 맞췄다. 저장소 안에 표기가 세 가지 섞여 있어 통일이 필요한 상태인데, 이번에는 눈에 띈 파일만 처리했다.

## 검증

데이터 파일을 실제로 망가뜨려 확인했다.

| 조작 | 결과 |
| --- | --- |
| 셀에 문자열 삽입 | 변환 실패 + 열 개수 + 행 개수, 세 건 보고 |
| 셀을 비움 | 위와 동일한 형태로 검출 |
| 행 하나 삭제 | 행 개수 불일치 |
| 중간에 빈 줄 삽입 | 읽기 종료 → 행 개수 불일치 |
| 열 하나 추가 | 열 개수 불일치 (기대 4 / 실제 5) |
| 파일명 변경 | 파일 오픈 실패 |

전부 게임 창이 뜨기 전에 종료됐다. 정상 파일로는 그대로 실행되고 네 방향 스프라이트도 정상 출력되는 것을 확인했다.

문자열 하나를 넣었을 때 에러가 세 줄 나오는 것은 연쇄다. 셀 변환이 실패해 그 셀이 빠지고, 그래서 열 개수가 모자라고, 그 행이 버려져 행 개수가 모자란다. 앞의 두 줄은 같은 줄 번호를 가리키므로 파일을 열면 한 곳을 보게 된다고 판단해 그대로 뒀다. 다만 마지막 행 개수 메시지는 위치를 가리키지 않아서, 이 부분은 다시 볼 여지가 있다.

## 커밋을 의도대로 나누지 못했다

커밋을 성격별로 나눌 계획이었는데 `RenderParser.cpp`에서 실패했다. 한 파일에 세 가지 축의 변경이 쌓여 있었기 때문이다. 네임스페이스 표기 전환, `LoadSpriteCSV` 재작성, `LoadMapCSV` 삭제.

첫 번째 때문에 파일 전체의 들여쓰기가 바뀌어 `git diff`가 파일을 통째로 하나의 덩어리로 잡았다. `git add -p`로 헝크를 골라내려 했으나 쪼갤 수 있는 형태가 아니었다. 결국 셋을 한 커밋에 넣고 메시지에 상황을 적었다.

**커밋을 나눌 수 있느냐는 작업 순서가 정한다.** 같은 파일에 여러 축의 변경을 쌓고 나면 나중에 분리할 방법이 없다. 표기 전환을 먼저 커밋하고 로직 작업을 시작했으면 셋 다 깨끗하게 갈렸을 것이다. 다른 파일이었던 `AnimationHelper.cpp`는 문제없이 분리됐다.

커밋 전에 `git diff`를 훑는 과정에서 의미 없는 공백 변경 두 곳도 찾아 되돌렸다. 지난 작업에서도 같은 것을 발견한 적이 있어 습관으로 남기고 있다.

한 가지 더. 공백이 들어간 경로를 따옴표 없이 넘겨 `git diff`를 확인했는데 결과가 비어 나왔다. 변경이 없어서가 아니라 명령이 매칭에 실패한 것이었고, git은 에러 없이 빈 결과를 낸다. 따옴표를 씌우니 정상적으로 나왔다. 빈 결과를 "문제없음"으로 읽으면 안 된다.

## 아직 안 된 것

- `InitAssets()`의 실패 플래그가 `SpriteCSV` 분기에만 연결돼 있다. 텍스처와 폰트는 로딩에 실패해도 경고만 출력하고 성공이 반환되며, `BeingTSV` / `DialogTSV` / `MapJSON`은 `bool`을 반환하는데 호출부가 받지 않는다. 반환값을 만드는 것과 받는 것이 별개라는 게 오늘 눈에 보였다.
- `LoadMapJSON`은 파일을 열지 못할 때만 실패를 알린다. JSON 파싱 에러, 타입 에러, 없는 키 접근은 여전히 예외가 밖으로 나간다.
- `InitAssets()`의 타입 분기에 `else`가 없어서, 매니페스트에 오타가 있으면 어느 분기에도 걸리지 않고 조용히 넘어간다.
- 네임스페이스 표기가 저장소 안에서 아직 통일되지 않았다. 오늘 두 파일만 손댔다.

## AI(Claude) 지원 범위

소크라테스식 튜터링 방식으로 진행했다. 코드는 직접 작성했다.

**받은 도움**

- 실패 경로를 먼저 세어보라는 유도. 처음에 세 개로 셌는데 `stoi` 경로를 빠뜨렸다는 지적을 받았다.
- 세 실패 경로가 같은 어서션 창을 띄웠다고 해서 원인이 같다고 결론지었는데, 그게 틀렸다는 지적. 실험이 우연히 극단적인 경우만 건드렸고, 열 밀림과 행 밀림은 원래 아무것도 터지지 않고 틀린 그림을 그리는 경로였다.
- 주석 내용이 확인한 사실과 반대라는 지적을 두 번 받았다. 코드를 열어 확인해놓고 문장으로 옮기는 사이에 뒤집혔다.
- `std::optional`을 검사 없이 역참조하는 코드를 짚어줬다. `if` 블록에 `continue`가 없어 그대로 흘러가는 형태였다.
- 검사를 넣을 위치에 대한 조언. 열 개수는 행을 다 읽은 뒤에야 확정되므로 안쪽 루프에서 검사하면 안 된다는 것.
- 호출부에서 지역 변수 이름이 멤버 변수를 가린 것, 같은 함수를 두 번 호출한 것, `return false` 위치가 잘못돼 실패 상태로 뒷부분이 실행되던 것.
- CR/LF의 유래와 `std::getline`이 `\r`을 남기는 이유에 대한 설명.
- 커밋 구성 제안. `RenderParser.cpp`를 분리할 수 없다는 것도 이 과정에서 드러났다.

**직접 한 것**

- 코드 작성 전부.
- 착수 전 실제 시그니처와 호출부 확인. 계획에 없던 `LoadMapCSV`를 발견한 것도 이 과정에서였다.
- 데이터 파일을 실제로 망가뜨려 실행하는 검증. Tiled 출력 파일 다섯 개를 열어 마지막 빈 줄을 확인한 것도 포함.
- 설계 판단들. `Direction`과 `AnimFrame` 중 어느 쪽 값을 남길지, 줄 정제를 어느 범위로 할지, 에러가 여러 줄 나오는 것을 감수할지.
- 링커 에러 원인 파악과 수정.
- 명명 규칙이 기존 코드와 어긋난다는 것을 발견하고, 다만 지금 고치면 범위가 커지므로 미루기로 한 판단.
