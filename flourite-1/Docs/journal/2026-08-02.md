# 2026-08-02 — 빌드 환경 정리와 실행 경로 문제

## 오늘의 목표

전날(8/1) 도입한 clone 후 빌드 검증에서 남은 과제인 `.vcxproj`의 SFML 절대 경로(`C:\SFML-3.1.0`) 정리부터 시작했다. 진행하는 과정에서 예상하지 않았던 문제가 두 건 더 드러나 함께 처리했다.

---

## 1. SFML 절대 경로 제거

### 문제

`.vcxproj`의 `AdditionalIncludeDirectories`와 `AdditionalLibraryDirectories`에 `C:\SFML-3.1.0`이 그대로 박혀 있었다. 다른 사람이 SFML을 다른 위치에 설치했다면 include를 찾지 못해 **컴파일 단계에서** 실패한다.

8/1의 clone 빌드 검증은 이 문제를 잡아내지 못했다. 검증을 같은 PC에서 했기 때문에 `C:\SFML-3.1.0`이 우연히 그대로 존재했고, 그때 발견된 것은 dll 누락(실행 단계 실패)뿐이었다. "내 환경에서 되는 것은 아무것도 증명하지 않는다"는 원칙이 clone 검증 자체에도 적용된다는 것을 확인한 셈이다.

### 처리

- 프로젝트 폴더 안에 `External Libraries/` 를 만들고, 그 아래 `SFML/` 에 라이브러리를 두는 구조로 정했다
- `.vcxproj`의 두 필드를 `$(ProjectDir)External Libraries\SFML\include` / `...\lib` 로 변경 (Debug|x64, Release|x64 각각, 총 4곳)
- `.gitignore`에 `flourite-1/External Libraries/*/` 추가 — 하위 폴더(라이브러리 실체)만 제외하고, 그 위의 안내 문서는 추적되게 했다
- `External Libraries/setup-guide.md` 작성 (영문). 다운로드 링크, 선택해야 할 패키지, 압축을 풀 위치를 명시

라이브러리를 추가할 때마다 `.gitignore`를 고치지 않아도 되도록 `*/` 패턴을 썼고, 안내 파일을 라이브러리 폴더 **바깥**(`External Libraries/` 바로 아래)에 둠으로써 SFML 자체의 `readme.md` 등과 섞이지 않게 했다.

### 폴더명 표기

`External Libraries`로 공백을 넣은 타이틀 케이스를 택했다. 기존 최상위 폴더들(`Header Files`, `Source Files`, `Resource Files`)이 같은 표기이기 때문이다. 같은 이유로 소문자였던 `docs`를 `Docs`로 통일했다.

대소문자만 바꾸는 폴더명 변경은 Windows 파일시스템이 대소문자를 구분하지 않아 git이 인식하지 못했다. `docs` → `docs-temp` → `Docs`로 중간 이름을 한 번 거치니 rename(100%)으로 정상 인식됐다.

### 검증

`git check-ignore -v`로 `.gitignore` 패턴이 실제로 SFML 폴더를 잡는지 확인한 뒤, `git ls-files`로 안내 문서만 추적되고 라이브러리 본체는 제외됐음을 확인했다.

## 2. SFML dll 자동 복사 (PostBuildEvent)

경로 문제를 고친 뒤에도 exe를 직접 실행하면 `sfml-graphics-d-3.dll` 누락 오류가 났다. 빌드에는 `.h`(선언)와 `.lib`(심볼)만 있으면 되지만, 실행에는 `.dll`(실제 코드)이 exe 옆에 있어야 하기 때문이다. 8/1에 "미결"로 남겨둔 항목이었다.

dll은 커밋하지 않는다는 기존 결정을 유지하고, 빌드 후 로컬 SFML에서 출력 폴더로 복사하는 방식을 택했다.

- `PostBuildEvent`로 `External Libraries\SFML\bin` → `$(TargetDir)` 복사
- 와일드카드(`*.dll`) 대신 실제로 링크하는 3개만 이름으로 명시. `AdditionalDependencies`에 있는 것과 1:1로 맞췄다
- Debug는 `-d-3.dll`, Release는 접미사 없는 이름으로 구성별로 분리

`x64\Debug\` 폴더를 통째로 지운 뒤 Rebuild해서, 세 dll이 이번 빌드에서 새로 생성됐음을 확인했다. 기존 파일이 남아 있어서 성공한 것처럼 보이는 상황을 배제하기 위한 절차였다.

## 3. 실행 위치에 따른 리소스 경로 문제

### 발견

dll 문제를 해결하자 exe가 오류 없이 실행됐지만 바로 종료됐다. 원인은 리소스 파일(TSV/INI)의 상대 경로였다.

Visual Studio에서 F5로 실행할 때는 작업 디렉터리가 프로젝트 폴더로 자동 설정되므로 `Resource Files/Config/...` 같은 상대 경로가 항상 맞아떨어졌다. 탐색기에서 `x64\Debug\flourite-1.exe`를 직접 실행하면 작업 디렉터리가 exe가 있는 폴더가 되어 리소스를 찾지 못한다.

지금까지 실행 확인을 IDE 안에서만 해왔기 때문에 드러나지 않았던 문제다.

### 처리

리소스를 출력 폴더로 복사하는 방식(에셋 파일 수가 많음)이 아니라, 프로그램 시작 시 작업 디렉터리를 프로젝트 루트로 한 번 고정하는 방식을 택했다. "실행 파일과 데이터의 위치 관계"는 파일을 읽는 모든 지점이 아니라 시작 시점 한 곳만 알면 되는 정보이기 때문이다. 이 방식이면 기존 파서 코드는 손대지 않아도 된다.

`Engine/Core/Utils/DirectoryHelper.h/.cpp` 추가:

- `GetModuleFileName`(Windows API)로 exe 전체 경로를 얻는다. 실행 중인 프로세스가 자기 위치를 아는 방법은 OS마다 다르고 C++ 표준에 없다
- 경로 조작은 `std::filesystem`으로 처리했다. `.parent_path()`를 세 번 호출해 솔루션 루트까지 올라간 뒤, 프로젝트 폴더명을 이어 붙인다. 폴더명 문자열은 호출부(`Application`)에서 넘긴다 — 범용 유틸리티가 특정 프로젝트의 폴더 이름을 알 이유가 없다
- 실패 시 빈 경로를 반환하고, 호출부에서 `.empty()`로 확인해 `Init`을 중단한다

`Application::InitConfigAndSystems()` 초입에서 `std::filesystem::current_path()`로 작업 디렉터리를 고정했다.

### 검증

경로를 출력해 `C:\Projects\custom_engine\flourite-1\flourite-1`이 나오는 것을 확인했고, 탐색기에서 직접 실행해 대사·메뉴·이동·NPC 동작까지 정상임을 확인했다.

### 남은 것

`current_path()`는 존재하지 않는 경로를 받으면 예외를 던질 수 있는데 지금은 감싸지 않았다. 폴더 구조가 다시 바뀌면 원인이 드러나지 않은 채 종료될 수 있다. 또한 이번 방식은 "솔루션 구조가 그대로 존재한다"는 전제에 기대고 있어, 출력 폴더만 떼어내 배포 가능한 형태로 만들려면 별도의 설계가 필요하다.

## 4. README 위치

8/1에 저장소 루트를 솔루션 폴더로 옮겼는데, README는 프로젝트 폴더에 남아 있었다. GitHub 저장소 페이지에서 처음 보이는 위치는 루트이므로, 방문자에게는 설명 없이 폴더와 `.sln`만 보이는 상태였다.

README를 루트로 옮기고 내부 경로 링크와 구성 설명을 `flourite-1/` 기준으로 수정했다. `.vcxproj`의 `<None Include="README.md" />` 항목은 파일이 프로젝트 폴더 밖으로 나가면서 Visual Studio가 자동으로 제거했다.
