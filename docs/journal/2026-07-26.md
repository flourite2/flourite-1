## 2. `ParseTsvTable` 크로스 파일 검증

지난주에 남겨둔 미검증 이슈였다. 템플릿 함수는 호출하는 번역 단위에서 본문 전체가 보여야 인스턴스화되는데, 당시에는 본문이 `CombatParser.cpp`에 있고 호출부도 같은 파일이라 우연히 동작하고 있었다.

### 처리

본문을 헤더로 옮겼다. 처음에는 `inline`을 붙이면 되는지 생각했는데, 템플릿 함수는 애초에 ODR 예외라서 `inline`이 논점이 아니었다. 핵심은 "호출부에서 본문이 보이느냐"였고, `inline`을 붙이든 말든 다른 `.cpp`에서는 여전히 본문을 볼 수 없다.

옮기는 김에 소속도 정리했다. `ParseTsvTable`은 `CombatParser`의 다른 멤버를 전혀 쓰지 않는 순수 함수였고, 앞으로 아이템·스킬 파서(Game 레이어 밖일 수 있음)가 쓸 예정이었다. `Engine/Core/Utils/TableParser.h`로 분리했다. 지난주에 "미결"로 남겼던 항목이다.

### 검증

`BeingParser.cpp`를 `ParseTsvTable` 기반으로 이관해 실제로 다른 번역 단위에서 호출했다. 컴파일·링크가 통과하고 스폰까지 정상 동작하는 것을 확인했다.

## 3. `std::function`을 템플릿 파라미터로 교체

리뷰 중에 `mapping` 파라미터가 `std::function`을 값으로 받고 있다는 지적을 받았다. 원시 타입이 아닌 것은 `const&`로 받는다는 내 원칙을 스스로 어기고 있었다. 함수도 참조로 받을 수 있다는 생각을 못 했던 것이 원인이다.

성능만 놓고 보면 파싱은 시작 시 1회라 타입 소거 오버헤드는 감당 가능한 수준이라고 판단했고, 그 판단 자체는 맞았다. 다만 `std::function` 껍데기를 걷어내고 템플릿 파라미터로 받으면 오버헤드도 사라지고 덤으로 얻는 것이 있었다.

지난주 일지에 "호출 시 템플릿 인자 `<T>` 명시 필수"라고 적어뒀는데, 그 원인이 정확히 "람다 → `std::function` 변환과 타입 추론이 동시에 필요해서"였다. `std::function`을 없애자 `T`는 두 번째 파라미터에서만 추론되면 되므로 `<T>` 없이 호출해도 컴파일된다. 실제로 확인했다.

**즉 지난주 기록은 "std::function을 파라미터로 쓸 때 한정"으로 조건이 좁혀져야 한다.**

## 4. 키 추출 책임을 호출부로

`ParseTsvTable` 안에 `mappingTable[mapped->id] = *mapped;`라는 줄이 있었다. 지난주에 "공통 함수 안에 특정 구조체 필드명이 등장하면 제네릭이 깨진 것"이라고 스스로 적어놓고, `id`는 규약으로 보고 넘어간 부분이다.

그런데 오늘 실제로 `id`가 없는 타입이 둘 나왔다. `RenderMapData`는 필드 자체가 없었고, `SpawnPointData`는 `entityID`였다.

### 판단

세 가지 선택지를 놓고 비교했다.

- 모든 `T`에 `id` 필드 강제 — `RenderMapData`의 `id`는 `name`의 사본이 되어 정규화 원칙에 걸리고, `entityID`라는 더 서술적인 이름을 덜 명확한 이름으로 바꾸게 된다
- 키 추출을 호출부 책임으로 — `COLSIZE` 검증과 타입 변환을 람다에 둔 것과 같은 기준
- 해당 타입은 `ParseTsvTable`을 안 쓴다 — 예외가 늘수록 "범용 파서"라는 이름값을 잃는다

두 번째로 갔다. 판단 기준은 지난주와 같다. **"그 지식을 아는 사람이 누구냐."** 키를 무엇으로 삼을지는 각 파서가 이미 알고 있고, 공통 함수는 모를수록 좋다.

### 구현

`mapping` 람다의 반환 타입을 `std::optional<std::pair<std::string, T>>`로 바꿨다. 키와 값을 한 쌍으로 돌려주고, `ParseTsvTable`은 `mappingTable[mapped->first] = mapped->second;`로 저장만 한다. 이제 공통 함수에 `T`의 필드명이 하나도 등장하지 않는다.

키 추출용 람다를 하나 더 받는 방식도 있었지만, 그 경우 키 재료가 `T`에 담기지 않은 컬럼이면 대응할 수 없다. 람다 안에서는 `cols`를 직접 보고 있으므로 항상 가능하다.

### 걸린 곳

`return { id, T{...} };`가 안 됐다. `optional` 생성자는 값 하나를 기대하는데 리스트가 오면 변환에 실패한다. 지난주에 겪은 것과 같은 문제였고, 일지에 적어둔 대로 `std::pair{ id, T{...} }`처럼 타입을 먼저 완성시켜 해결했다.

`mapped.first`도 안 됐다. `optional`의 포장을 벗기지 않은 것이다. 이것도 지난주 기록에 있었다. `mapped->first`로 고쳤다.

**두 번 다 지난주에 적어둔 항목을 다시 밟았다.** 기록해둔 덕에 에러 메시지를 보고 바로 원인을 찾을 수 있었지만, 애초에 적어둔 것을 먼저 확인했다면 더 빨랐을 것이다.

## 5. 빈 줄 처리 순서와 그로 인해 드러난 것

`ParseTsvTable`이 헤더 스킵을 빈 줄 검사보다 먼저 하고 있었다. 파일 첫 줄이 빈 줄이면 그것이 헤더로 소비되고 진짜 헤더가 데이터로 취급된다. 순서를 뒤집어 "첫 번째 유효한 줄이 헤더"가 되도록 고쳤다.

그런데 이 수정 직후 `baseDef` 값이 0으로 나오기 시작했다.

### 원인 추적

`defTable.size()`를 찍어 2가 나오는 것을 확인했다. 파싱은 되고 있었다. 다음으로 테이블의 실제 키를 전부 출력했더니 `npc_default`는 값이 정상인데 `player`만 0이었다.

`base_defense_table.tsv`를 열어보니 **헤더 행이 `#`로 시작하고 있었다.** 수정된 순서에서는 `#` 행이 주석으로 걸러지고, 그 다음 줄(실제 데이터 첫 행인 `player`)이 헤더로 간주되어 통째로 스킵된 것이다. 수정 전 순서에서는 `#` 헤더가 헤더 스킵에 먼저 걸려 우연히 동작하고 있었다.

파서 규칙을 정리하자 데이터 파일이 규칙을 안 지키고 있었다는 사실이 드러난 셈이다. 다른 tsv는 모두 `#` 없는 헤더였으므로 이 파일 하나를 고쳐 통일했다.

### 함정 1번을 다시 밟은 것

원인을 좁히는 데 시간이 걸린 이유가 하나 더 있었다. 조회 코드가 `defTable["player"]`처럼 `[]`를 쓰고 있었다. `unordered_map::operator[]`는 없는 키에 접근하면 0으로 초기화된 항목을 조용히 만들어낸다. 그래서 "값이 0이다"와 "데이터가 없다"를 화면상으로 구분할 수 없었다.

지난주 일지 함정 1번에 그대로 적어둔 내용이다. `at()`이나 `find()`를 썼다면 즉시 알았을 것이다. 읽기 목적의 `[]` 조회를 전부 정리하는 것을 다음 과제로 남겼다.

## 6. 죽은 코드 발견

`ParseAttackConfig` 이관에 앞서 `ParseRenderConfig`를 보고 있었는데, `RenderMapData`에 `id` 필드가 없다는 것을 발견했다. 키를 무엇으로 삼아야 할지 판단하려고 실제 tsv를 열어보니 컬럼 매핑도 코드와 어긋나 있었다.

호출부를 검색해봤다.

```
ParseRenderConfig → 검색 결과 2건 (선언과 정의뿐, 호출 0건)
```

**아무도 부르지 않는 함수였다.** `urban_rpg_asset_sfml_map.tsv`도 읽히지 않고 있었다.

`RenderMapData`는 `AnimationHelper::Initialize`가 쓰고 있어서 처음에는 살아있는 줄 알았다. 그런데 `Initialize`의 호출부도 0건이었다. 참조가 있다고 살아있는 것이 아니라, **죽은 함수가 죽은 함수를 참조하고 있었다.**

실제 에셋 로딩은 `Application::InitAssets()`가 `asset_manifest.tsv`를 읽어 타입별로 분기하는 방식이었다. 화면에 스프라이트가 정상적으로 그려지고 있었던 것은 이쪽 경로 덕분이다.

`AnimationHelper::GetRectFromTileID`는 `BeingFactory`가 실제로 쓰고 있으므로 파일 통째로 지우면 안 된다. `Initialize`와 전용 전역 변수만 정리 대상이다.

### 이관 목록을 만들 때 놓친 것

딕셔너리의 파서 현황 표에 `RenderParser`는 아예 없었는데 코드에는 존재했다. **이관 대상을 정할 때 "호출되고 있는가"를 먼저 확인하지 않았다.** 그대로 진행했다면 죽은 코드를 정성껏 리팩토링했을 것이다.

`AnimationHelper::Initialize` 안에는 `bindAnim(Direction::Down, AnimFrame::Walk1, "player_wdl");` 같은 하드코딩이 12줄 있었고, 로그는 "Data-Driven Runtime Address Mapping Success"를 찍고 있었다. 데이터 주도 설계를 표방하면서 매핑 자체는 코드에 박혀 있었던 셈이다. 플레이어 전용이라 NPC가 여럿인 현재 구조와도 맞지 않는다.

## 7. 부수적으로 정리한 것들

이관 작업 중에 걸린 것들이다.

- **`FileLoader::LoadFile`의 `extension` out 파라미터 제거** — `ParseTsvTable`이 받아놓고 쓰지 않고 있었다. 호출부를 검색하니 `InputParser`가 확장자로 tsv/ini 분기를 하고 있었는데, 실제 입력 매핑 파일은 ini 하나뿐이라 tsv 분기는 죽은 코드였다. 파일명도 `input_map.ini`에서 `input_config.ini`로 바꿨다(테이블이 아니라 config이므로).
- **`std::string filepath` → `const std::string&`** — `InputParser`만 값 전달이었다. 솔루션 전체 검색으로 통일했다. 검색 결과에 지난주 일지가 잡혔는데, 거기에 "`string`은 원시 타입이 아니다"라고 이미 적어놓고 정작 코드는 안 따라가고 있었다.
- **`BeingFactory::SpawnBeing` 헤더/구현 분리** — 함수 본문이 헤더에 있었다. 지금은 include하는 `.cpp`가 하나라 문제가 없지만 둘이 되는 순간 중복 정의가 난다. `.cpp`로 옮긴 뒤에도 같은 에러가 났는데, 헤더는 이미 고쳤고 `Application.obj`가 옛 결과물을 재사용하고 있었던 것이다. Rebuild로 해결했다. 기본 인자는 선언 쪽에만 두어야 한다는 것도 다시 확인했다.

## 8. 파서 이관 완료

`ParseTsvTable` 기반으로 5개를 이관했다.

| 파서 | 비고 |
|---|---|
| `ParseDefenseConfig` | 지난주 완료분을 `pair` 방식으로 수정 |
| `ParseBeingConfig` | 크로스 파일 검증용, 구버전 컬럼 fallback 분기 제거 |
| `ParseAttackConfig` | `COLSIZE` 4 → 5 수정 |
| `ParseStatConfig` | `beingId`를 구조체 첫 필드로 이동 |
| `ParseElementalConfig` | `modified` 계열 초기화 추가 |

### `ParseAttackConfig`의 COLSIZE

지난주에 요확인으로 남겨둔 항목이다. `const int COLSIZE = 4;`로 검증하면서 본문에서 `cols[4]`까지 읽고 있었다. 실제 tsv는 5컬럼이었으므로 5가 맞다.

다만 지난주 추정과 실제는 달랐다. 검증이 `<`(부족하면 스킵)였기 때문에 `5 < 4`는 거짓이라 통과했고, 파싱은 정상 동작 중이었다. **버그는 잠복 상태였고, 컬럼이 정확히 4개인 행이 들어오는 순간에만 범위 밖 접근으로 터진다.** 검증 상수를 `!=`로 통일해 이런 불일치가 즉시 드러나게 했다.

컬럼 수가 바뀌면 `cols[n]`을 읽는 코드도 반드시 함께 바뀌므로, 관용적으로 통과시키는 것보다 즉시 실패하는 쪽이 일관된다고 판단했다.

### `Elemental`의 modified 값

임시로 `base + 1.0f`를 넣었다가 출력이 `base: 1, modified: 2`로 나오는 것을 보고 되돌렸다. 버프가 하나도 없는 상태에서 원소 배율이 2배로 잡히는 값이었고, 그대로 두면 나중에 전투 계산에 그대로 들어간다. "임시"라는 주석이 붙어 있어도 틀린 값은 위험하다.

지난주에 남긴 요확인 항목(`ADD_FINAL` 자리의 항등원이 `1.0f`인 것이 의도인지 실수인지)과 같은 뿌리로 보인다. 데미지 계산식을 만들 때 함께 정리한다.

### 이관하지 않은 것

- `DialogParser` — `unordered_map`이 아니라 `vector`에 저장하고 ID 정렬 후 이진 탐색을 쓴다. 자료구조가 달라 현재 시그니처로는 들어가지 않는다. 중첩 Split과 `try/catch`도 있어 성격이 다르다
- `RenderParser::LoadSpriteCSV` / `LoadMapJSON` — CSV/JSON 기반
- ini 계열 로직

`ParseTsvTable`을 컨테이너 종류까지 제네릭하게 확장하는 선택지도 있지만, "공통 함수는 모를수록 좋다"는 오늘의 판단 기준에 비추면 지금 확장할 이유가 없다.

## 9. AI에게 받은 도움 / 직접 한 것

**AI에게 받은 것**

- `Select-String`, `git` 명령어의 문법과 옵션. PowerShell 환경에 익숙하지 않아 명령어 자체는 대부분 제시받았다
- 빈 검색 결과를 재검증하는 방법(존재가 확실한 패턴으로 테스트해보기)
- 템플릿 함수와 ODR의 관계, `inline`이 왜 이 문제의 해법이 아닌지에 대한 설명
- `std::function`을 템플릿 파라미터로 바꾸는 방법과, 그것이 템플릿 인자 추론 문제까지 해결한다는 지적
- `std::pair` 문법
- 원칙 위반 지적 — 값 전달로 받은 `std::function`과 `std::vector`, 매직 넘버, 죽은 분기, 부정확한 주석 등
- 커밋 메시지 구성과 커밋을 나누는 기준

**직접 한 것**

- 모든 코드 작성과 수정
- 키 추출 책임을 어디에 둘지, 컬럼 수 검증을 `<`로 할지 `!=`로 할지 등의 설계 판단
- `baseDef`가 0으로 나오는 문제의 원인 추적. `size()` 확인 → 실제 키 목록 출력 → tsv 파일 확인 순으로 범위를 좁혀 `#` 헤더에 도달했다
- 죽은 코드 판별. 호출부 검색 결과를 보고 `ParseRenderConfig`와 `AnimationHelper::Initialize`가 모두 호출되지 않는다는 것을 확인했다
- 각 명령의 실행과 결과 판단

**AI의 판단을 검증한 사례**

`git diff`로 어제 일지의 변경 내역을 확인할 때, AI가 앞부분만 보고 "섹션이 통째로 덮어써졌다"고 판단했다. 전체를 끝까지 확인해보니 실제로는 섹션 제목이 바뀌고 내용은 새 섹션으로 이동한 것이었고, 잃어버린 내용은 없었다. diff에서 "삭제 + 다른 위치에 추가"는 이동인데 앞부분만 보면 삭제로만 보인다.

## 10. 남은 과제 / 다음 세션 시작점

### 우선 처리

1. **읽기 목적의 `[]` 조회를 `at()` / `find()`로 교체** — 오늘 원인 추적이 늦어진 직접적 원인이다. `Table[` 검색으로 후보를 찾는다. 저장 목적의 `[]`는 그대로 둔다
2. **죽은 코드 삭제 마무리** — `ParseRenderConfig`, `RenderMapData`, `AnimationHelper::Initialize`와 전용 전역 변수. `GetRectFromTileID`는 살아있으므로 파일째 삭제 금지
3. **`engine_config.ini`의 `[Paths]` 미사용 키 정리** — `AssetManifest`만 살아있는 것으로 보인다. `"Paths."` 검색으로 확인
4. 신규 테이블 파서 구현(아이템 / 장비 / 스킬) + 문자열 → enum 변환 함수

### 요확인 항목

- **컬럼명과 코드 변수명 불일치** — tsv는 `BeingID`, `Attack`이고 구조체는 `beingId`, `baseAtk`다. "config 컬럼명은 코드 변수명과 정확히 일치"라는 원칙에 어긋난다. 구조체 필드를 개명할지, 원칙 문구를 조정할지 판단 필요. 파급 범위가 넓어 별도 작업으로 분리
- **`ElementType` 개수 `5`가 여러 곳에 흩어져 있음** — 파싱 루프 2곳, `COLSIZE`, `std::array<float, 5>` 선언. 원소를 하나 추가하면 전부 따로 고쳐야 하고 하나라도 놓치면 조용히 깨진다. 한 곳에서 관리할 방법 필요
- **`StatParser`의 성장 곡선 상수** — `maxExp = 10.0f + level * 10.0f`, `maxLevel = 25`. 매직 넘버이며, 밸런싱 대상이므로 `being_config.ini` 후보
- **`currentExp + 10.0f`** — EXP 바 표시 확인용 임시값. 변동치 테이블 도입 시 제거
- `modified` 계산식의 `ADD_FINAL` 항등원 (지난주부터 이월, 데미지 계산식 작성 시 정리)
- `DialogParser` 이관 여부

## 오늘의 회고

원래 계획은 30분짜리 확인 두 건을 마치고 파서 이관에 집중하는 것이었다. 실제로는 이관에 도달하기까지 여러 번 옆길로 샜고, 중간에는 "왜 이렇게 진전이 없나" 하는 생각도 했다.

다만 샌 길들이 대체로 같은 성격이었다는 점은 남길 만하다. `_OldFiles` 검색의 빈 결과, `#`로 시작하던 헤더, 아무도 부르지 않는 파서, 값 전달로 받고 있던 `std::function` — 전부 "확인하지 않고 넘어갔던 것"이 뒤늦게 드러난 경우였다. 특히 `ParseRenderConfig`를 그대로 이관했다면 죽은 코드를 리팩토링하는 데 시간을 썼을 것이다.

과거에 AI에게 통째로 맡겨둔 부분들이 이런 형태로 남아 있다는 것도 확인했다. 동작은 하지만 구조가 어긋나 있거나, 참조는 있는데 실행되지 않는 코드들이다. 지금 발견해서 다행이라고 생각한다.

지난주 일지에 적어둔 항목을 오늘 두 번 다시 밟았다(`optional` 반환과 포장 벗기기). 기록해둔 덕에 에러를 보고 바로 원인을 찾긴 했지만, 코드를 쓰기 전에 먼저 펼쳐봤다면 애초에 밟지 않았을 것이다. 기록은 쌓았으니 다음은 참조하는 습관 쪽이다.
