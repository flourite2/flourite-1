# 진행 요약 (2026.03.29 ~ 2026.07.17)

> Git 도입 이전 기간의 개발 기록 요약. 이 시기의 상세 로그는 저장소에 포함되어 있지 않으며, 아래는 주요 설계 판단과 구현 이력을 단계별로 정리한 것이다.

---

## Phase 1 — 시간 시스템 기초 (3월 말 ~ 4월 중순)

- DeltaTime 개념 학습 및 `Timer` 클래스 직접 구현 (chrono 기반). 가변 프레임의 문제(환경별 게임 속도 차이), accumulator 누적과 오버헤드 이월 원리 정리
- Timer의 한계 4가지(프레임 제한 없음, 클램핑 없음, 타임스케일 없음, accumulator 단일) 자체 진단 후 개선
- **가변 스텝 vs 고정 타임스텝의 구조적 차이 정리** — "렌더링 주기에 물리가 종속되면 안 된다"는 원리. 물리 주기 100Hz로 결정
- 역할 분리 설계: Timer(시간 측정) / TimeManager(배율) / Interval(주기) / Renderer(출력) / Logic(물리)

## Phase 2 — 물리/수학 기초 + SFML 도입 (4월 중순 ~ 5월 초)

- `Vector2D` 직접 구현 (연산자 오버로딩)
- 중력 미구현 결정 — 탑뷰 2D에는 불필요. 범용성보다 목표 우선
- **SFML 채택** — SDL2 / Raylib과 비교 후 C++ 기반 및 학습 목적 적합성을 근거로 선택. 라이브러리 링킹, DLL 배치 등 환경 구축
- `RigidBody`, `PhysicsSystem2D`(OOP 버전) 구현 — force 기반 이동, 활성/비활성 개체 관리

## Phase 3 — 에셋 파이프라인 + 렌더링 (5월)

- **Kenney RPG Urban Pack 채택** — CC0 라이선스 에셋만 사용한다는 원칙 수립
- 486개 타일의 이름 매핑 문제를 수식 / CSV / enum 3방식 비교 후 해결
- 스프라이트 시트 기반 렌더링, 타일맵 구현
- 5/23: 충분히 이해하지 못한 채 작성한 부분을 재점검하는 세션 진행 (Timer의 nanoseconds 전환 등)

## Phase 4 — 벤치마킹 + OOP→ECS 전환 (6월 초)

- `PerformanceTracker` 구현 — ΔT / Allocation / DrawCall / Swap 4지표 측정, CSV 내보내기 + Python(matplotlib) 그래프화
- **ECS 전환** — 전환 근거를 3관점에서 정리: 설계(God Object 방지), 하드웨어(캐시 라인·패딩), CPU(프리패처 예측)
  - 다만 **OOP → ECS로의 코드 전환 작업 자체는 생성형 AI에 위임**했다. 판단(왜 전환하는가)은 직접 내렸으나 변환된 코드를 처음부터 직접 쓰지는 않았다
  - 이후 전환된 코드를 읽고 이해하는 세션을 별도로 진행했고, 이 시점을 기준으로 개발 방식을 **"AI 생성 위주 + 사후 이해"에서 "직접 구현 + 막힐 때 질문"으로 전환**했다
  - 이 프로젝트에서 AI 활용 범위는 각 개발 일지에 기록하고 있다

## Phase 5 — 맵 / 대화 / 데이터 구동 설계 (6월 중순 ~ 7월 초)

- **Tiled 도입** — 레이어 분리(Ground / Walls), 충돌 영역을 JSON export로 파싱. nlohmann/json 채택
- 6/14: "루프 내 Allocation 0회, 성능, 범용성" 3원칙 수립. `main.cpp` → `Application` 이전 시작
- **대화 UI 시스템** — 타이프라이터 연출(줄바꿈 1회 캐싱 + 인덱스 증가), UTF-8 / SFML 인코딩 문제 해결, 나인슬라이스 렌더링 구현
- **`asset_manifest.tsv` 도입** — 경로 하드코딩 전면 제거, 데이터 구동 리소스 파이프라인 구축
- Application 1차 분리: `BeingFactory` / `AnimationUpdater` / `UIUtils`

## Phase 6 — 메뉴 + 스탯 파이프라인 (7월)
