## 5. `ParseDefenseConfig` 버그 수정 (지난주 이월 항목)

### 증상

`base_defense_table.tsv`는 정상적으로 읽히는데, 정작 `defTable`에서 값을 꺼내면 비어 있었다.

```
[playerDefComp Test]
baseDef: 0
modifiedDef: 0
```

### 원인 추적 과정

범위를 좁혀 가며 확인했다.

1. 파일 로드 실패인가? → 파서 내부에서 로그를 찍어보니 `id: player / defaultDef: 1`까지는 정상. **로드는 성공**
2. 타입 불일치인가? → `DefenseMapData` 구조체 확인. **문제 없음**
3. 파싱 직후 테이블을 출력 → `id:`가 **빈 문자열**, 값도 0. 즉 **테이블에 아무것도 안 들어갔다**

### 원인

루프 마지막에 **테이블에 저장하는 줄 자체가 없었다.**

```cpp
data = { id, currentDef, modifiedDef };
// defTable[data.id] = data;   ← 이 줄이 통째로 누락
```

로컬 변수 `data`는 루프가 끝나면 사라진다. 참조(`&`)로 받은 `defTable`은 "저절로 채워지는 것"이 아니라 **명시적으로 대입해야만** 값이 들어간다.

### 교훈

- 참조 파라미터는 "출력 통로"일 뿐, 대입하지 않으면 아무 일도 일어나지 않는다
- 다른 파서(`ParseAttackConfig`)와 **나란히 놓고 비교**하니 5분 만에 보였다. 같은 역할의 코드가 여러 벌 있으면 diff가 곧 디버깅 도구가 된다
- 동시에 이건 **"같은 코드를 여러 벌 복붙해둔 구조 자체의 문제"**이기도 하다. 저장하는 줄이 파서 개수만큼 존재하니, 그중 하나만 빠뜨려도 이런 버그가 난다 → 다음 작업으로 이어짐

## 6. `ParseTsvTable<T>` — 제네릭 TSV 파서 도입

### 문제 인식

파서 4~5개가 전부 아래를 **토씨 하나 안 다르게 복붙**하고 있었다.

```
파일 로드 → 헤더 스킵 → 빈 줄/주석 스킵 → \t 분리 → (테이블별 조립) → 맵에 저장
```

처음엔 "테이블마다 1번째는 float, 2번째는 string, 3번째는 int라 함수화가 불가능한 것 아닌가" 싶었다.
하지만 **공통 부분과 가변 부분의 경계를 정확히 그으면** 해결되는 문제였다.

### 설계 결론 — "그 지식을 아는 사람이 누구인가"

| `ParseTsvTable` (공통, 1회 작성) | `mapping` 람다 (파서마다 작성) |
|---|---|
| 파일 로드, 헤더/주석 스킵 | 컬럼 개수 검증 (`COLSIZE`) |
| `\t` 분리 → `cols` 생성 | `Trim`, `stof`/`stoi` 등 타입 변환 |
| `mapping(cols)` 호출 | `T` 구조체 조립 후 반환 |
| `mappingTable[mapped->id] = *mapped;` | — |
| **컬럼 수·타입·필드명을 일절 모름** | 자기 테이블 스펙을 전부 앎 |

판단 기준은 단순했다. **`stof`를 쓸지 `stoi`를 쓸지 아는 사람이 누구인가?** `base_defense_table.tsv`의 2번째 컬럼이 float라는 걸 아는 건 공통 함수가 아니라 `ParseDefenseConfig`를 작성하는 나 자신이다. 따라서 그 지식은 호출부에 남기고, 공통 함수는 아무것도 모르는 채로 뼈대만 돌린다.

`COLSIZE`도 같은 이유로 호출부에 둔다. 실제로 `cols[0]`, `cols[1]`에 인덱스 접근하는 코드가 람다 안에 있으므로, **검증은 접근 지점 가까이** 있어야 한다.

### 최종 시그니처

```cpp
template<typename T>
void ParseTsvTable(const std::string& filepath,
                   std::unordered_map<std::string, T>& mappingTable,
                   std::function<std::optional<T>(const std::vector<std::string>&)> mapping);
```

### 시그니처를 확정하기까지 걸렸던 것들

시그니처 한 줄 완성하는 데 여러 번 고쳤다. 각각이 나름의 이유가 있었다.

| 잘못 쓴 것 | 왜 틀렸나 |
|---|---|
| `unordered_map<string, T*>` | `T`가 이미 "타입을 대신하는 이름표"인데 포인터를 한 겹 더 씌울 이유가 없다. 기존 테이블 타입과도 안 맞는다 |
| `std::string filepath` | `string`은 원시 타입이 아니다. 복사 비용이 있으므로 `const&` |
| `std::vector<std::string&>` | vector는 원소로 참조를 담을 수 없다. `&`는 vector **바깥**에 붙어야 한다 |
| `const std::vector<std::string>` (& 없음) | `const`만 있고 `&`가 없으면 여전히 복사가 일어난다. 둘이 같이 있어야 "복사 없이 읽기 전용" |
| 람다 반환 타입 `T` | 실패 시 "이 줄은 스킵"을 알릴 방법이 없다 → `std::optional<T>` |

### `std::optional`을 쓴 이유

람다 안에서 `continue`를 써도 **바깥 함수의 루프는 건너뛸 수 없다**. 람다는 별개의 함수이기 때문이다.
따라서 "이 줄은 유효하지 않으니 건너뛰라"는 신호를 **반환값으로** 전달해야 했고, 그 용도가 `std::optional`이다.

- 실패: `return std::nullopt;`
- 성공: `return T{ ... };`
- 공통 함수 쪽: `if (mapped) { mappingTable[mapped->id] = *mapped; }`

## 7. 오늘 부딪힌 컴파일 에러들

리팩토링 후 에러가 20개 가까이 쏟아졌다. 하나씩 정리하니 실제 원인은 훨씬 적었다.

### (1) IntelliSense 에러 ≠ 실제 빌드 에러

Error List 기준 15개 → **Rebuild Solution 후 실제 에러 4개.**
`#include <optional>`이 분명히 있는데도 `namespace "std" has no member "optional"`이 뜨는 시점에서 의심했어야 했다. 딕셔너리 함정 3번에 이미 적어둔 내용인데 또 걸렸다.

### (2) `return { id, baseDef, modifiedDef };` → 변환 실패

```
'return': cannot convert from 'initializer list' to 'std::optional<DefenseMapData>'
```

`std::optional`의 생성자는 **"T 하나"**를 기대하는데 값 3개짜리 리스트를 던져줬다. `optional`이 "이 셋으로 먼저 T를 만들고 그걸 감싸야겠다"고 알아서 판단해주지 않는다.
→ `return DefenseMapData{ id, baseDef, modifiedDef };`로 **T를 먼저 완성**시켜야 한다.

### (3) 람다 → `std::function` 변환 시 템플릿 추론 실패

```
no instance of function template "ParseTsvTable" matches the argument list
cannot convert argument 3 from '<lambda_1>' to 'std::function<...>'
```

람다의 타입과 `std::function`의 타입은 다르다. 컴파일러 입장에서는 **"`T`를 알아야 변환할 수 있는데, 변환해봐야 `T`를 알 수 있는"** 순환에 빠진다.
→ `ParseTsvTable<DefenseMapData>(filepath, defTable, mapping);`처럼 **템플릿 인자를 명시**해야 한다.

이 과정에서 `<>`의 위치와 내용도 여러 번 틀렸다.

- `mapping<DefenseMapData>()` — 템플릿인 건 `ParseTsvTable`이지 람다 변수가 아니다
- `ParseTsvTable(..., ParseTsvTable<DefenseMapData>(mapping))` — 함수를 두 번 호출하는 꼴이 됐다. `<T>`는 **한 번의 호출에 타입 정보만 덧붙이는 표시**다
- `ParseTsvTable<std::optional<DefenseMapData>>` — `T`는 테이블에 저장되는 완성된 구조체 타입이다. `optional`은 함수 시그니처 내부에서만 씌워졌다 벗겨지는 것이지 `T` 자체가 아니다

### (4) 진짜 범인 — 헤더의 중괄호 하나

마지막까지 남은 에러 20여 개의 정체는 **`CombatParser.h`의 `namespace` 블록에 `}`가 하나 더 붙어 있었던 것**이었다.

중괄호 짝 하나가 어긋나자 컴파일러가 그 지점부터 모든 스코프를 잘못 해석하면서:

- `std::optional` / `std::function`을 못 찾는다는 에러
- 방금까지 잘 쓰던 `mapping`, `cols`가 `identifier not found`
- `'CombatParser::ParseDefenseConfig': 'void' function returning a value`

가 동시에 쏟아졌다.

> **가장 유용했던 단서**: `void` 함수가 값을 리턴한다는 에러. 이건 "**람다 안의 `return`이 바깥 함수의 것으로 해석됐다**" = 중괄호 스코프가 깨졌다는 강력한 신호다. 에러 개수에 압도되지 말고 **가장 위쪽 에러부터, 그리고 중괄호 짝부터** 확인할 것.

## 9. 저장소 위생 정리

문서를 정리하다가, 공개 저장소에 들어가면 안 되는 파일이 이미 커밋되어 있다는 것을 발견했다.

### 발견한 것

- `docs/project-dictionary.md` — 개인 일정 관련 서술이 포함된 작업용 문서. 원래 저장소 바깥에서 관리할 문서였다
- `docs/journal/2026-07-19.md` — 지난주 일지에도 같은 성격의 문구가 1행 남아 있었다
- `Header Files/_OldFiles/`, `Source Files/_OldFiles/` — ECS 전환 이전의 구버전 코드 48개 파일

### 처리

파일을 지우는 커밋을 새로 쌓아도 **과거 커밋에는 그대로 남는다.** 커밋이 2개뿐인 초기 단계였으므로, 히스토리를 새로 시작하는 쪽을 택했다.

```
git checkout --orphan <새 브랜치>   # 부모 없는 브랜치 (작업 트리는 유지)
git reset                          # 인덱스 비우기
git add . / git status / git commit
git branch -D main / git branch -m main
git push -f origin main
```

`_OldFiles`와 딕셔너리는 `git rm --cached`로 **인덱스에서만 제거**했다. 디스크의 파일은 남으므로 로컬 빌드에는 영향이 없다. 이후 `.gitignore`에 등록해 재발을 막았다.

### 검증

작업 후 다음을 실행해 히스토리 전체를 확인했다.

```
git ls-files | Select-String "<제외 대상>"
git rev-list --all | ForEach-Object { git grep -i "<민감 문자열>" $_ }
```

`git grep`은 기본적으로 현재 커밋만 검색하므로, `git rev-list --all`과 조합해 **모든 커밋을 훑어야** 한다.

### 교훈

- **지웠다고 생각한 것을 명령으로 다시 확인한다.** 딕셔너리만 확인하고 끝냈다면 지난주 일지에 남은 1행은 놓쳤을 것이다. 검증 명령이 그것을 잡아냈다
- **`git add .` 후 `git status`를 눈으로 훑고 커밋한다.** 오늘 발견한 문제는 모두 "확인 없이 올림"에서 나왔다
- PowerShell에서 한글 문자열 `git grep`은 인코딩 문제로 실패할 수 있다. `Select-String`을 쓰거나 결과가 비어 있을 때 명령 자체를 의심해야 한다. 실제로 초기에 "결과 없음"을 "깨끗함"으로 잘못 읽을 뻔했다

### 남은 과제

`.vcxproj` / `.filters`가 `_OldFiles`를 참조하고 있다면, 저장소를 클론한 사람은 빌드가 깨진다. 프로젝트에서 제외 처리 후 Rebuild 확인이 필요하다. (미확인)

## 10. AI 활용 기록

이 프로젝트는 AI가 대신 짜준 코드를 붙여넣지 않는 것을 원칙으로 한다. 오늘 실제로 받은 도움의 범위를 남겨둔다.

**받은 도움**

- 튜터 모드(완성 코드 제공 금지, 질문과 힌트 위주)로 대화를 진행했다. 파서 구조를 "공통 뼈대 + 테이블별 람다"로 나누는 방향은, 스스로 답하기 어려워 여러 차례 질문을 받으며 좁혀간 결과다
- 람다 기본 문법(`[캡처](매개변수) -> 반환타입 { 본문 }`), `std::function`을 매개변수로 쓰는 형태, `std::optional`의 값 확인(`if (opt)`)과 해제(`*opt`, `opt->`) 방법은 직접 물어보고 설명을 들었다
- 컴파일 에러 메시지를 어떻게 읽어야 하는지(위쪽 에러가 아래를 오염시킨다는 점, `void` 함수가 값을 리턴한다는 에러가 중괄호 스코프 문제의 신호라는 점)에 대한 힌트를 받았다. 헤더의 중괄호 짝을 확인해보라는 방향 제시도 받았다
- `ParseAttackConfig`의 `COLSIZE`와 modified 계산식 문제는 내가 아니라 AI가 코드를 읽다 지적한 것이다 (11번 요확인 항목)
- 딕셔너리 갱신본과 이 일지의 초안 작성

**직접 한 것**

- 모든 코드 작성과 수정. 시그니처를 여러 번 틀리고 고치는 과정도 직접 거쳤다
- `ParseDefenseConfig` 버그의 원인 추적 (로드 → 타입 → 테이블 순으로 범위를 좁혀 누락된 저장 줄에 도달)
- 레포 재구성 및 정체성 정리, .vcxproj 문제 발견 및 수정, 빌드 환경 정리
- 저장소 위생 정리(히스토리 재작성, 인덱스 정리, 검증) 실행. 절차와 검증 명령은 AI에게 제시받았고, 각 단계의 결과 판단과 실행은 직접 했다

**남는 과제**

람다와 템플릿은 질문 없이 혼자 쓰기에는 아직 익숙하지 않다. 다음 세션에서 Attack/Elemental 파서를 이관할 때는 같은 패턴이므로, 되도록 묻지 않고 먼저 써본 뒤 검토를 받는 방식으로 진행해보려 한다.

## 11. 남은 과제 / 다음 세션 시작점

### 우선 처리

1. **`ParseTsvTable` 크로스 파일 사용 검증** (5~10분, 워밍업)
   현재 템플릿 본문이 `CombatParser.cpp`에 있고 호출부도 같은 파일이라 동작한다. 하지만 템플릿은 **호출하는 번역 단위에서 본문이 보여야** 인스턴스화된다. 향후 `ItemParser.cpp` 등 다른 `.cpp`에서 호출하면 링커 에러가 날 가능성이 있다.
   → 헤더로 본문 이동 vs 명시적 인스턴스화 중 택일. **신규 파서 착수 전에 반드시 확인**
2. `ParseAttackConfig` / `ParseElementalConfig`를 `ParseTsvTable` 기반으로 이관
3. 신규 테이블 파서 구현 (아이템 / 장비 / 스킬) + 문자열 → enum 변환 함수

### 오늘 발견한 요확인 항목

- ⚠ **`ParseAttackConfig`의 `COLSIZE` 값** — `const int COLSIZE = 4;`로 검증하는데 본문에서 `cols[4]`까지 읽는다. 컬럼이 정확히 4개인 행이 들어오면 **범위 밖 접근**. 실제 tsv 컬럼 수(id + atk + critRate + critRatio + speed = 5)와 대조 필요
- ⚠ **`ParseAttackConfig`의 modified 계산식** — `modifiedX = ((currentX + 0.0f) * 1.0f) + 1.0f;`
  곱셈 항등원 `1.0f`는 맞지만, 마지막 `ADD_FINAL` 자리도 `1.0f`로 되어 있다. 버프 미적용 상태라면 덧셈 항등원인 `0.0f`여야 하지 않은가? 의도인지 복붙 실수인지 확인 필요
- `ParseTsvTable`의 소속 — `CombatParser`의 다른 멤버를 전혀 쓰지 않는 순수 함수다(`PhysicsUtils::CalculateForce`와 같은 성격). Combat에 둘지, 별도 유틸 네임스페이스로 뺄지 미결. 아이템/스킬 파서가 쓰기 시작하면 결정해야 한다

## 오늘의 회고

계획 변동과 환경 정리에 시간을 많이 써서 코드 작업 착수가 늦었고, 후반에는 집중력도 떨어졌다. 결과적으로 파서 리팩토링은 Defense 하나만 마쳤다.

오늘의 성과는 Defense 파서 버그 수정 및 리팩토링이었다.

이해했다고 생각하고 넘어간 C++ 기초를 다시 사용하게 되었다. 너무 오랜만에 보는 요소들이라 다시 익히면서 이해하는 데 시간이 꽤 걸렸다.

템플릿 + 람다 + `std::optional`을 조합한 콜백 주입 패턴을 처음부터 끝까지 직접 조립해봤고, 그 과정에서 값/참조 전달, 템플릿 인자 추론의 한계, `optional`의 포장/해제 같은 모던 C++의 기본기를 실제 컴파일 에러를 통해 몸으로 익혔다.

비록 지금은 파서 하나 수정이지만, 차후 Application 대규모 리팩토링을 하기 전 파서들 또한 리팩토링을 진행하면 될 것으로 보인다.

후반에는 예정에 없던 저장소 정리에 시간을 썼다. 계획된 작업은 아니었지만, 공개 저장소를 다루는 이상 한 번은 겪었어야 할 일이라고 생각한다.

에러 20개 앞에서 당황했지만, "위쪽 에러 하나가 아래를 오염시킨다"는 원리를 붙잡고 범위를 좁혀 결국 중괄호 하나까지 도달한 것도 나쁘지 않았다.
